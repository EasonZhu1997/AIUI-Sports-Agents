# AIUI Sports Agents 开源项目怎么玩：从跑步、骑行到划船机，做一套可验证的运动 Agent

戴着智能眼镜跑步、骑车或使用划船机时，我们真正需要的，通常不是把手机上的数据面板缩小后搬到眼前，而是一个知道什么时候该说、该说什么，也知道什么时候应该保持沉默的运动伙伴。

这正是 **AIUI Sports Agents** 想要探索的问题。

它不是把几个运动 Demo 放进同一个仓库，也不是用一个总分比较跑步和骑行谁“更智能”。我们希望建立一套面向智能眼镜的、证据优先的运动 Agent 方法：真实传感器优先，估算数据明确标注，拿不到的数据保持不可用；每一次提示都能说明依据，每一项结论都能回到版本、设备和测试记录。

首批将从三个最容易形成完整闭环的场景开始：跑步、骑行和划船机。

## 三个项目，验证同一套方法

跑步 Agent 关注配速、步频、距离、心率与训练阶段。它需要在用户不方便看屏幕时，用尽量少的提示帮助维持节奏，并在信号不稳定或数据不足时避免做出过度判断。

骑行 Agent 关注速度、踏频、距离、心率，以及设备实际支持的功率等指标。它不仅要正确读取数据，还要处理停车、断连、重连、传感器抢占等真实问题。设备没有功率能力时，界面和总结都不应把推算值包装成实测值。

划船机 Agent 则关注桨频、时间、距离、配速和划行阶段。首期会优先支持可验证的数据通路，例如设备提供的标准蓝牙服务；厂商私有协议只有在有明确文档和真实设备证据时才进入支持列表。它也会成为检验这套方法能否从户外迁移到室内器械的重要样本。

三个应用会保持独立：各自拥有清晰的代码、版本、能力声明和专项测试。它们又共享同一套数据可信度规则、生命周期约定、交互安全原则和评测框架。这样既能复用基础能力，又不会用“万能运动算法”掩盖不同运动之间真正的差异。

## 这个开源项目具体怎么玩

先分清许可层：当前根层评测、治理和公共工具 Hub 采用 Apache-2.0；Run、Bike、Rower 的完整应用源码已位于 `apps/`，分别采用 PolyForm Noncommercial 1.0.0 与单独书面商业许可，属于 source-available。公开可查看不等于获得商业使用权。

你可以用四种方式参与。

第一种是直接体验。选择一个运动项目，按照项目页准备支持的设备和传感器，先运行模拟数据或回放样例，再进入 Reader、预览环境或真机验证。每个项目都会列出“已验证”“待验证”和“仅设计”能力，避免把能编译、能预览与能在真实运动中稳定使用混为一谈。

第二种是开发新的运动 Agent。开发者可以复用公共契约，把传感器输入转换成带来源和质量状态的标准数据，再实现运动自己的状态机、提示策略和总结逻辑。Hub 的契约与应用实现遵循各自许可证；应用源码贡献应进入对应的 `apps/<project-id>/` 目录，并在 CLA 正式启用后按其流程提交。一个最小可用的 Agent 不需要功能很多，但应完成“采集—判断—提示—记录—复盘”的闭环。例如，划船机可以先只做好桨频、分段配速和断流恢复，再逐步加入训练计划，而不是一开始就堆满无法验证的指标。

第三种是做评测。你可以拿同一设备、同一固件和同一测试脚本，对不同版本进行复测；也可以提交新的边界场景，例如跑步暂停后恢复、骑行停车不虚增、划船机短暂断流后重连。评测的价值不在于制造漂亮数字，而在于帮助复现问题，并说明结果适用到什么范围。

第四种是贡献证据。一次真实设备测试、一个可复现的失败样例、一段去敏后的原始数据，往往比新增十个界面功能更有价值。贡献时请同时写清设备型号、固件、应用版本、操作步骤、期望与实际结果；涉及个人运动轨迹或健康数据时，应先去除身份和位置等敏感信息。

## 不设一个模糊总分：三层评测各司其职

项目采用 `Common / Sport / Evidence` 三层结构。

**Common** 是所有运动共享的底线，包括首次出数时间、数据断流与恢复、前后台生命周期、误触控制、低打扰交互、离线能力、隐私处理和构建复现。它回答的是：这个 Agent 是否具备成为可靠产品的基本条件？

**Sport** 是运动专项指标。跑步测配速、步频与暂停恢复；骑行测速度、踏频、停车判定与多传感器行为；划船机测桨频、距离、分段配速与设备状态变化。它回答的是：在这个具体运动里，数据和策略是否真的有用？专项分只用于同一运动、同一测试条件下的版本比较，不用来宣称“骑行比跑步高几分”。

**Evidence** 不是另一个性能分数，而是证据等级。单元测试、模拟回放、构建通过、Reader 或预览验证、真实设备验证、完整现场对照，代表不同强度的结论。结果卡必须绑定版本、设备、测试条件和日期；没有真机证据，就明确写“待真机验证”。

这三层合在一起，能让“功能完成了”变成一个可追问、可复测的说法。

## 本地能证明什么，真机还要证明什么

本地环境适合证明代码结构、协议解析、算法逻辑、自动化测试和构建产物是否成立；模拟数据适合稳定复现边界条件；Reader 或预览环境适合检查界面和基本交互。

但这些不能自动证明蓝牙扫描与权限、真实传感器兼容性、长时间运动中的断连恢复、佩戴状态下的可读性、户外误触、安全性和功耗。真实设备测试仍是独立关卡。项目会把两类证据分开记录，也不会因为本地测试通过就把某项能力标成“真机已支持”。

这条边界看起来保守，却是开源项目建立信任的关键：不知道就是不知道，尚未验证就公开写出来，让下一位贡献者知道最值得补哪一块。

## 路线图：先把闭环做实，再扩运动品类

第一阶段会建立项目总览、公共契约、项目登记表、评测规范和结果卡模板，并整理跑步、骑行、划船机三个示例的最小可复现版本。

第二阶段聚焦真实设备矩阵和同场测试：补齐常见传感器与器械的兼容记录，完善断流、恢复、暂停、停车和异常数据等测试脚本，让结果可以由其他人复测。

第三阶段再沉淀可复用的 Agent 能力，包括训练阶段识别、低打扰提示策略、可追溯总结和跨项目组件。划桨、马术等更多运动可以进入实验区，但只有达到明确的证据门槛，才升级为稳定项目。

我们希望最终形成的不是一个“功能很多”的展示仓库，而是一套任何开发者都能审阅、运行、质疑和改进的运动 Agent 实验场。

如果你想参与，最好的起点不是先问“还能加什么功能”，而是选择一个运动场景，跑通最小闭环，记录一次可复现测试，然后提交一份诚实的结果卡。智能眼镜上的运动 Agent，真正值得开源的，不只是代码，还有把它做可靠的方法和证据。
