# 项目生命周期

总项目用项目轨道表达建设和兼容性承诺，不用它替代证据等级。一个 `candidate` 项目的某项能力仍可能只有 L1；一个 `incubating` 项目也可能对少数场景提供 L4 证据。

## 状态

### `incubating`

适用于问题、传感器来源或公共接口仍在探索的项目。要求：

- 有明确场景、用户问题和维护者；
- 列出数据来源、权限、隐私与现实安全风险；
- 不借用其他项目的成熟度或真机结论；
- 所有公开页面明确标注实验性和开放门。

### `labs`

适用于已有可运行探索实现、但公共契约或硬件范围仍快速变化的项目。至少要求：

- 有范围说明、构建入口、自动化测试和失败语义；
- 采用公共证据等级、结果身份和隐私/安全基线；
- 有维护者处理问题和依赖更新；
- 明确标注实验性，不承诺接口稳定或广泛硬件兼容。

### `candidate`

适用于进入公开发布准备的项目。除 `labs` 要求外，还应：

- 有经过白名单设计的源码导出方式与第三方清单；
- 发布前列出 L2–L5 已完成项和未完成项；
- 有清晰的版本、迁移、回滚和公开结果计划；
- 关键失败状态、隐私边界和安全门均有自动化回归。

### `stable`

适用于接口相对稳定并持续维护的项目。除 `candidate` 要求外，还应：

- 公布兼容范围和版本策略；
- 在至少两个独立版本/测试周期中重复关键真机验证；
- 有依赖、安全问题和回归测试的维护记录；
- 对破坏性变更提供迁移或明确的版本边界。

## 初始项目表

| 项目 | 当前轨道 | 当前边界 |
| --- | --- | --- |
| Run | `candidate` / 首发准备 | 跑步专项指标独立评测，真实与估算来源分开 |

| Rider | `incubating` / 孵化组 | 先固定场景、传感器和安全契约 |

首发准备与首发观察都只是首轮公开建设范围，不表示应用源码已经发布、完成 L4/L5 或适配所有设备；应用源码是否可见及其许可状态单独判断。

## 状态变更

申请变更需提交：

1. 目标状态和理由；
2. 维护者及响应范围；
3. 测试矩阵与证据索引；
4. 数据流、权限、安全与第三方审计；
5. 兼容性、迁移与回滚方式；
6. 仍开放的真实设备门。

进入 `stable`、加入/退出首发准备或观察范围、降级轨道或重新激活停止维护的项目属于高影响决策，按 [GOVERNANCE.md](../GOVERNANCE.md) 评审。项目不会仅因时间经过、下载量或演示效果自动升级。
